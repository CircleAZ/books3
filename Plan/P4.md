## 1. Core Technical Specifications

### 1.1 ID Generation & Database
*   **Primary Keys**: All database tables must use **UUID (v4)** as the primary key (`id`) to ensure global uniqueness and data integrity.
*   **Display IDs**: The user-friendly IDs defined below are for **Display Purposes Only** (`display_id`).
    *   **Format**: **Auto-Incrementing Integer** (Scoped to Store/Tenant).
    *   **Structure**: Simple integer sequence (e.g., 1001, 1002, 1003).
    *   **Prefixes**: Optional UI-only prefixes can be displayed (e.g., "ORD-1001"), but the database stores the integer `1001`.
    *   **Starting Value**: Sequences should start at a reasonable number (e.g., 1000) to appear established.
    *   **Offline Handling**:
        *   **Provisional ID**: When created offline, generate a temporary string ID (e.g., `TEMP-UUID-1`).
        *   **Visual Indicator**: Mark these items with a "Sync Pending" icon or asterisk.
        *   **Sync Logic**:
            1.  Client sends `TEMP-ID` record to Server.
            2.  Server saves record, assigns the next available Integer ID (e.g., `1050`).
            3.  Server responds with the new `display_id`.
            4.  Client updates local record to show `1050`.
            5.  **UUID**: The underlying UUID (`id`) remains constant throughout, ensuring relationships (like Order Items linked to Order) never break.

### 1.2 Offline Support (PWA)
*   **Architecture**: Progressive Web App (PWA).
*   **Service Worker**: Cache critical UI assets (HTML/CSS/JS) for offline access.
*   **Local Storage**: Use `IndexedDB` to store:
    *   Draft Orders (created while offline).
    *   New Customer records (created while offline).
*   **Sync**: Background Sync API to push offline data to the server when connectivity returns.
*   **Conflict Resolution Strategy**: **Last Write Wins (Server Authority)**.
    *   To simplify the user experience for cashiers, the system will prioritize the latest update.
    *   **Logic**: If a record is modified offline and also modified on the server, the server's version (or the latest timestamped version) takes precedence.
    *   **Exception**: Critical financial records (like Order Status) may block sync and require manual intervention if a conflict is detected.

### 1.3 Map Integration
*   **Provider**: **Leaflet.js** (Frontend) + **OpenStreetMap** (Tiles).
*   **Geocoding**: **Nominatim** (OSM) for address-to-coordinate conversion.
    *   **Data Storage Optimization**:
        *   **Do NOT** store the full JSON response object from the geocoding API.
        *   **Store Only**: `latitude`, `longitude`, and the **Full Display Address String**.
        *   **Benefit**: Reduces database size while preserving the exact address text seen by the user.
    
### 1.4 Technology Stack
*   **Backend**: **Django** (Python).
*   **API**: **Django REST Framework (DRF)**.
*   **Database**: **PostgreSQL**.
*   **Frontend**: PWA Client (React or Vue SPA) consuming DRF APIs.
*   **Authentication**: JWT / Token-based auth via DRF.

3.  **Manage Order Statuses (Detailed State Machine)**
    *   3.1. **Payment Status**: (Pending, Partial, Completed, Overpaid)
    *   3.2. **Delivery Status**: (Pending, Processing, Completed)
    *   3.3. **Return Status**: (NA, Item Received, Completed, Cancelled)
        *   3.3.1. **NA** (Default): No return process initiated.
        *   3.3.2. **Item Received**: Customer has returned items, awaiting further processing (e.g., inspection, refund).
        *   3.3.3. **Completed**: Return process is finished (e.g., items restocked/discarded, refund processed if applicable).
        *   3.3.4. **Cancelled**: A return request was made but then cancelled.
    *   3.4. **Refund Status**: (NA, Pending, Partial, Completed, Cancelled)
        *   3.4.1. **NA** (Default): No refund process active.
        *   3.4.2. **Pending**: Refund initiated, awaiting processing/payment.
        *   3.4.3. **Partial**: Part of the refund amount has been processed/paid.
        *   3.4.4. **Completed**: Full refund processed/paid.
        *   3.4.5. **Cancelled**: A refund request was initiated but then cancelled.
    *   3.5. **Cancellation Status**: (NA, Pending, Completed, Cancelled)
        *   3.5.1. **NA** (Default): Order is not undergoing cancellation.
        *   3.5.2. **Pending**: Request to cancel the order has been made, awaiting confirmation/processing.
        *   3.5.3. **Completed**: Order has been successfully cancelled.
        *   3.5.4. **Cancelled**: A cancellation request was made but then itself was cancelled (i.e., order proceeds).
    *   3.6. **Order Status (Derived - Primary User-Facing Status)**:
        *   The system will evaluate conditions in the following order of precedence:
        *   3.6.1. **If Cancellation Status IS Pending**:
            *   Then Order Status = **"Cancellation Pending"**
            *   (Regardless of other statuses, if an order cancellation is actively pending, this takes precedence).
        *   3.6.2. **Else If Cancellation Status IS Completed**:
            *   3.6.2.1. If (Payment Status IS Partial OR Payment Status IS Completed OR Payment Status IS Overpaid) AND (Refund Status IS NA OR Refund Status IS Pending OR Refund Status IS Partial):
                *   Then Order Status = **"Action Needed"** (Reason: Order cancelled after payment, refund required/pending).
            *   3.6.2.2. Else (Cancellation is Completed, and either no payment was made, or refund is already Completed/Cancelled):
                *   Then Order Status = **"Order Cancelled"**
        *   3.6.3. **Else If (Cancellation Status IS NA OR Cancellation Status IS Cancelled)**:
            *   (This block handles orders that are not actively cancelled or whose cancellation was reversed).
            *   3.6.3.1. If (Return Status IS Item Received) AND (Refund Status IS NA OR Refund Status IS Pending OR Refund Status IS Partial):
                *   Then Order Status = **"Action Needed"** (Reason: Returned items received, refund/resolution pending).
            *   3.6.3.2. Else If (Payment Status IS Overpaid) AND (Refund Status IS NA OR Refund Status IS Pending OR Refund Status IS Partial):
                *   Then Order Status = **"Action Needed"** (Reason: Order was overpaid, refund for overage is pending).
            *   3.6.3.3. Else If (Delivery Status IS Completed) AND (Payment Status IS Pending OR Payment Status IS Partial):
                *   Then Order Status = **"Delivered - Awaiting Payment"**
            *   3.6.3.4. Else If (Delivery Status IS Completed) AND (Payment Status IS Completed OR Payment Status IS Overpaid) AND (Return Status IS NA OR Return Status IS Completed OR Return Status IS Cancelled) AND (Refund Status IS NA OR Refund Status IS Completed OR Refund Status IS Cancelled OR (Payment Status IS Overpaid AND Refund Status IS Completed)):
                *   (This checks if the core order is fulfilled and any associated return/refund processes are also concluded or not active. If overpaid, the refund for the overage must be completed).
                *   Then Order Status = **"Order Complete"**
            *   3.6.3.5. Else (if none of the above specific states in 3.6.3 apply):

## 4. Messaging System (Architecture B: Secured Android Gateway)

**Goal**: Zero-cost, reliable SMS delivery using personal SIMs and Android devices, secured and monitored.

### 4.1 Architecture Overview
*   **Gateway Nodes**: Android phones running Termux + Python Flask + Cloudflare Tunnel.
*   **Backend**: Django Application with a `MessageQueue` system.
*   **Communication**: Backend pushes requests to Cloudflare URLs; Phones execute SMS via Android API.
*   **Security**: **API Key Authentication** for all requests between Backend and Gateway.
*   **Reliability**: **Heartbeat Monitoring** to detect offline phones and failover automatically.

### 4.2 Database Schema (`MessageQueue`)
*   **Table**: `MessageQueue`
    *   `id` (UUID)
    *   `phone_number` (String)
    *   `content` (Text)
    *   `message_type` (Enum: SMS, WHATSAPP)
    *   `status` (Enum: PENDING, PROCESSING, SENT, FAILED)
    *   `gateway_used` (String, e.g., "SIM_1")
    *   `attempts` (Integer, Default 0)
    *   `error_log` (Text)
    *   `created_at` (Timestamp)
    *   `updated_at` (Timestamp)

### 4.3 Workflow (Dispatcher)
1.  **Trigger**: Event occurs (e.g., Order Created).
2.  **Backend**: Creates a `MessageQueue` record with status `PENDING`.
3.  **Dispatcher (Cron/Celery)**:
    *   Fetches `PENDING` messages.
    *   **Load Balancing**: Selects a Gateway using Round-Robin (0-90 msgs -> SIM 1, 91-180 -> SIM 2).
    *   **Heartbeat Check**: Pings `/heartbeat` on the Gateway. If offline, marks Gateway as unavailable and retries with another.
    *   **Send**: POSTs to Gateway URL with `X-API-Key`.
    *   **Update**: Sets status to `SENT` or `FAILED` (increments attempts).

### 4.4 Anti-Blocking Strategy (Spintax)
*   **Rule**: Never send the exact same text 100 times.
*   **Implementation**: Use Spintax templates (English & Gujarati) to vary message content.
